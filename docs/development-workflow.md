# 開発とGitの作業手順

## この手順の目的

Codexが実装・検証を進め、ユーザーがレビュー・承認・判断を行うための共通手順です。アプリの変更だけでなく、設定や文書の整備にも適用します。

## 基本用語

| 用語 | 意味 |
| --- | --- |
| ブランチ | 変更を進めるために分けた作業の流れ |
| 差分 | 変更前と変更後の違い |
| コミット | ローカルのGitに変更を記録すること |
| プッシュ | ローカルのコミットをGitHubに送ること |
| プルリクエスト（PR） | 作業ブランチの変更をレビューし、取り込みを依頼する窓口 |
| マージ | 作業ブランチの変更を取り込み先のブランチへ統合すること |

プッシュだけでは`main`に変更は取り込まれません。作業ブランチをGitHubへ送り、PRを通じて`main`へ取り込みます。

## ブランチの方針

- `main`はレビュー・承認済みの変更を取り込むブランチとします。
- 通常の作業には`feature/<作業内容>`を使います。機能追加だけでなく、修正や文書整備も当面はこの形式に統一します。
- 作業内容は短い英語の小文字とハイフンで表します。今回の例は`feature/setup-development-workflow`です。
- 1つの作業ブランチとPRでは、1つの目的にまとまる変更を扱います。

## 依頼から取り込みまで

| 順番 | 担当 | 作業と完了条件 |
| --- | --- | --- |
| 1 | ユーザー | 目的、期待する動作、制約を伝える。Codexは不明な点を確認する |
| 2 | Codex | 作業場所とGitの状態を確認し、作業用ブランチを用意する |
| 3 | Codex | 依頼の範囲で変更し、必要なテストと差分確認を行う |
| 4 | Codex | 変更内容、確認結果、未確認事項を示し、レビューできる状態にする |
| 5 | ユーザー | VS Codeなどでレビューし、修正を依頼するか、コミット・プッシュ・PR作成を承認する |
| 6 | Codex | 承認された変更をコミットし、作業ブランチをプッシュしてPRを作成する |
| 7 | ユーザー | PRと確認結果を見て、`main`へのマージを判断する |
| 8 | ユーザーまたはCodex | ユーザーがマージする。Codexが代行する場合は明示的なマージ指示を受けて実行する |

### 承認の扱い

- ファイルの作成・変更を依頼されたら、Codexはその範囲の編集と検証を進めます。
- コミット・プッシュ・PR作成は、具体的な変更内容を確認できる状態で承認を得ます。「この内容でコミット・プッシュしてPRを作成して」のようにまとめて承認できます。
- すでに同じ変更範囲について明示的な指示・承認がある操作は、再確認せず進めます。
- マージはプッシュやPR作成と分けて判断します。PR作成の承認だけではマージしません。
- 承認後に仕様や変更範囲が大きく変わった場合は、変更点を示して再確認します。
- ブランチ保護などGitHub側の強制ルールは別途設定するものです。この文書を追加するだけでは有効になりません。

## CodexのGit操作

以下のコマンドは手順の例です。通常はCodexが実行し、ユーザーがすべて手入力する必要はありません。

### 1. 作業開始時の確認

```sh
pwd
git rev-parse --show-toplevel
git status --short --branch
git remote -v
```

未コミットの変更がある場合は内容を確認し、ユーザーの変更を保護します。作業中のブランチがある場合は、新規作業か継続作業かを判断し、むやみに切り替えません。

新規作業を開始する場合は、作業ツリーがクリーンであることを確認してから`main`を更新し、ブランチを作ります。

```sh
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feature/setup-development-workflow
```

ブランチ名は依頼に合わせて変更します。`--ff-only`で更新できない場合は履歴を調査し、強制的なリセットや意図しないマージで解消しません。

### 2. 変更とレビュー

- Codexは変更に応じた確認を行い、実施した内容と結果を報告します。
- 文書のみの変更は内容・リンク・差分を確認します。コードの変更は整備済みのテストや起動手順に従います。
- VS CodeではCodexと同じ作業フォルダを開き、「ソース管理」から差分を確認します。新規ファイルは全文を確認します。
- Git worktree（別の作業フォルダ）を利用する場合は、Codexがそのパスを伝え、ユーザーは同じフォルダを開きます。
- `git diff`では未追跡の新規ファイルは表示されないため、`git status`と新規ファイルの内容も確認します。

### 3. 承認後のコミット・プッシュ・PR作成

今回の2ファイルを扱う例です。対象を明示してステージし、コミットに含まれる内容を確認します。

```sh
git add AGENTS.md docs/development-workflow.md
git diff --cached --check
git diff --cached
git commit -m "docs: 開発ルールとGit作業手順を追加"
git push -u origin feature/setup-development-workflow
gh pr create --base main --head feature/setup-development-workflow \
  --title "開発ルールとGit作業手順を整備" --body-file /path/to/pr-body.md
```

`/path/to/pr-body.md`は例示用のパスです。Codexが目的・変更内容・確認結果を記した一時ファイルを作成し、その実際のパスに置き換えます。認証情報や実データをPR本文に含めません。

プッシュ後はリモートへの反映を確認し、ブランチ名・コミットID・PRのリンクを報告します。ネットワークや認証に問題があれば、その時点までに完了した操作と未完了の操作を区別します。

## 開発環境の前提

- 開発の依頼はデスクトップアプリのCodexで行い、VS Codeでも変更を確認します。
- Mac上のソースコードを利用し、アプリの実行・テスト環境はColimaとDockerで整備する予定です。
- デスクトップ側のCodexが自動的にDev Container内で実行されるとは限らないため、環境構築時に共通の起動・テストコマンドを定めます。
- 使用言語、フレームワーク、起動・テストコマンドは現時点では未決定です。決定後に文書を更新します。
- Git操作はGit、PR操作はGitHub CLI（`gh`）で行えます。GitHubプラグインの追加を必須とはしません。
