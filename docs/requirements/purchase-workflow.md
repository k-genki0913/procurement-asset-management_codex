# 購入申請の閲覧・操作と発注資料（相談中）

更新日：2026-10-17

## 目的と範囲

PR #8以降の相談で合意した購入申請の認可・状態ごとの操作・発注記録・添付資料をまとめます。[会社・業務の前提](business-context.md)を共通の前提とし、申請者の役職・金額による承認ルートは[認証・認可と購入承認の要件](authentication-authorization.md)を参照します。

要件定義は継続中です。下記の状態名は業務を説明するもので、DBやAPIの設計を確定するものではありません。機能の実装順序・初期リリース範囲は別途決めます。

## 閲覧範囲（合意済み）

| 対象 | 閲覧できる人・内容 |
| --- | --- |
| 提出前の下書き | 申請者本人だけ |
| 提出済みの申請 | 申請者本人、申請した課の全員、その部署の部長 |
| 却下・取消・購入中止の申請 | 上記と同じ範囲。状態・理由・経緯を確認できる |
| 差戻し中の申請 | 本人は編集中の内容を閲覧可能。他の閲覧者には直前の提出内容と差戻し理由を表示 |
| 差戻し後の再提出 | 修正内容が課内・部長へ公開される |
| 発注関連資料 | その申請と同じ閲覧範囲。差替え前資料の将来の制限は未決定 |

- 同じ部署でも別の課の申請は原則閲覧できません。部長は自部署全体の提出済み申請を、課・金額・部長承認の要否によらず閲覧できます。他部署の申請や社員の下書きは対象外です。
- 当初の「非管理職社員は自分の申請のみ閲覧」という案を更新し、課内共有を採用しました。二重申請の発見と発注時の情報共有が目的で、自動的に重複を防ぐ機能ではありません。
- 閲覧できても、他人の申請内容を編集したり、承認権限なしで承認したりすることはできません。アカウント管理権限だけで全社の申請を閲覧できるとは扱いません。
- 異動・兼務時にどの時点の所属を参照するかは未決定です。

## 編集・終了・再提出（合意済み）

### 編集

申請者本人が下書き・差戻し中に限り編集できます。提出したら直接編集できません。承認者も内容を書き換えず、修正が必要なら差し戻します。承認完了・却下・取消・購入中止の元の内容も編集できません。

### 操作の意味と権限

| 操作 | 行う人・条件 | 結果 |
| --- | --- | --- |
| 却下 | 承認者 | その申請は終了する |
| 差戻し | 承認者 | 申請者へ修正を求め、同じ申請を修正・再提出できる |
| 取消 | 申請者。差戻し中、または今回の提出に対してまだ誰も承認していない承認待ち | 申請を取り下げる |
| 購入中止 | 最終承認者。承認完了後かつ実際に未発注の場合 | 承認の記録を残したまま購入を中止する |

却下・差戻し・取消・購入中止は理由コメントを必須とし、操作した人・日時とともに残します。理由は申請の閲覧者が確認できます。

- 非管理職社員の承認待ちの申請は、課長が承認する前まで本人が取消可能です。
- 課長自身の申請は、部長が承認する前まで本人が取消可能です。
- 課長承認済み・部長承認待ちで中止したい場合は、申請者が部長へチャット等で依頼し、部長が経緯を理由に残して却下します。却下後に申請者がさらに取り消す操作は不要です。
- 承認完了後は本人の通常取消を禁止します。未発注なら、課長承認で完了したものは課長、部長承認まで行ったものは部長が購入中止を記録します。依頼は当面チャット等で行い、別の中止依頼ワークフローは設けません。
- 発注済みの場合は購入先へのキャンセル確認が必要で、アプリの状態変更だけで注文は消えません。発注後のキャンセル手順は未決定です。

### 差戻しからの再提出

- 申請者が同じ申請を修正して再提出し、通常の承認ルートの最初からやり直します。
- 再提出時の金額などからルートを再判定します。非管理職社員なら課長から、課長自身の申請なら部長から開始します。
- 修正前の内容、差戻し理由、過去の承認履歴を残します。以前の承認を修正後の内容への承認として流用しません。
- 再提出後の取消可否は今回の提出に対する承認で判定し、過去の提出に対する承認は数えません。

### 却下後の新規申請

却下された申請は終了のまま残し、購入内容等をコピーして新しい下書きを作れます。新しい申請番号を付け、元の申請との関連を残し、承認は最初から行います。元の却下理由・承認履歴を変更しません。コピーする項目の詳細は未決定です。

## 発注（合意済み）

- 承認は会社が購入を認める判断です。購入先は申請者が探し、発注者は申請者や申請した課で決めます。購入先を把握している課で進め、総務課へ業務を集中させないためです。
- 発注者を事前に割り当てる機能や承認フローは設けず、課内で調整します。
- 注文自体はアプリの外で行い、実際に発注した課員本人が「発注済み」を記録します。承認が完了し、購入中止になっていない申請が対象です。
- 実際の発注者・発注日時と、記録した人・記録日時を残します。
- アプリの未発注表示と実際の注文状況が異なる期間があり得ます。購入中止を行う最終承認者は、実際に未発注かを課内で確認する運用です。

## 発注関連資料（合意済み）

| 項目 | ルール |
| --- | --- |
| 必須条件 | 発注済みの記録時に1件以上添付 |
| 形式 | PDF・JPEG・PNG |
| 容量 | 1ファイル10MBまで。バイト換算の定義は設計時に明確にする |
| 件数 | 1申請につき、現在有効な資料が最大10件 |
| 資料の例 | 発注書、注文確認書、注文完了メールのPDF、注文完了画面の画像 |
| 差替え | 発注済みを記録した本人が、理由を必須入力して行える |
| 差替え履歴 | 元の資料と操作者・日時・理由を残す。差替え前資料は10件に数えない |

- 発注後には注文完了メールなどが手元にある想定のため、任意添付案は採用しません。資料で購入先・注文内容・数量・金額等を確認できることを意図します。
- 添付が完了するまでは発注済みに更新しません。アップロード失敗時に実際の注文とアプリ表示がずれるリスクがあります。
- ファイルの存在と、正しい注文の資料であることは別です。内容の確認担当は未決定です。
- 差替え前の資料を件数に含めない理由は、上限に達しても誤りを修正できるようにするためです。元資料の履歴保存分も容量を使います。

### 過去資料の保管案（未確定）

一定期間後の削除、S3等の保存コストが低い場所への移動、特定権限だけに取得を許可する案があります。いずれも採用・保存期間・保存先・取得権限は未決定です。S3利用やライブラリ追加を決定したものではありません。削除する場合は、過去の発注根拠を確認できなくなる影響を検討します。

## 確認例

| 条件 | 期待する結果 |
| --- | --- |
| 同じ課の別の社員が下書きを閲覧 | 拒否 |
| 同じ課の別の社員が提出済み・却下・取消の申請を閲覧 | 許可。状態・理由を確認できる |
| 部長が自部署の少額申請を閲覧 | 部長承認が不要でも許可 |
| 差戻し中に申請者が金額を変更 | 本人のみ編集中の内容を閲覧。他の閲覧者には直前の提出内容を表示 |
| 差戻し後に再提出 | 修正内容を公開し、ルートを再判定して最初から承認 |
| 提出済みの内容を本人または承認者が直接編集 | 拒否 |
| 非管理職の申請で今回の課長承認がまだない | 本人が理由付きで取消可能 |
| 今回の課長承認済み・部長承認待ちで本人が取消 | 拒否。部長が中止依頼を理由付きで却下して終了 |
| 再提出直後に、過去の提出で承認履歴がある本人が取消 | 今回の承認がまだなければ許可 |
| 却下・差戻し・取消・購入中止の理由が未入力 | 操作を完了できない |
| 承認完了・未発注で申請者が通常取消 | 拒否。最終承認者による購入中止を使う |
| 発注済みの記録で資料が0件 | 完了できない |
| 有効な資料が10件の状態で、本人が1件を理由付きで差替え | 有効資料は10件のまま。元資料も履歴に保持 |
| 有効資料を11件にする／10MBを超えるファイルを添付 | 拒否 |
| 発注記録者以外の課員が資料を差替え | 閲覧可能でも差替えは拒否 |

## 未決定事項・実装前に確認する点

- 異動・兼務時の閲覧範囲、申請課の確定時点、承認者変更・代理承認、不在・退職時の資料差替え。
- 承認者による却下・差戻しが可能な段階の詳細、承認と取消など同時操作時の扱い、下書きの削除。
- 承認金額と実際の発注金額・数量が異なる場合、分割発注、複数購入先、発注後のキャンセル・訂正・返品。
- 注文番号・購入先・発注日を独立項目として持つ案と各項目の必須性、コピー項目、添付資料の後日追加・単純削除の可否。
- 拡張子に加えた実体検証、ダウンロード時の権限確認など添付の安全対策の具体設計。保存容量管理、資料の保管期間・削除・移行は未決定。
- 発注前の重複注文防止、資料の内容確認、注文済みだが記録できない場合の対応。
