# 会社・業務の前提

更新日：2026-10-01

## この文書の目的と状態

別の開発セッションでも同じ前提から相談・判断できるよう、会話で合意した架空の会社の設定を記録します。要件定義は継続中です。未決定事項や説明用の例を、確定した仕様として実装しないでください。

認証・認可と購入承認のルールは[認証・認可と購入承認の要件](authentication-authorization.md)を参照します。変更時は判断理由と関連文書への影響を確認し、合意内容を更新します。

## 開発目的・進め方（合意済み）

- 個人開発で、業務アプリを題材にサーバー側の開発と要件定義を学びます。実在企業の業務を再現するものではありません。
- 保守性・変更容易性を重視し、リリース頻度が高く、障害発生の少ないシステムを目指します。具体的な品質目標や確認方法は未決定です。
- ユーザーが要件・優先順位・仕様を判断し、レビュー・承認します。Codexが調査・提案・文書化・実装・検証を担当します。
- 小さなPRを順番にレビューし、依存ライブラリは必要になった時点で追加します。[開発手順](../development-workflow.md)に従います。
- 現在の相談の目的は認証・認可の要件定義です。今回の文書化は機能実装の開始を意味しません。

## 会社と組織（合意済み）

架空の1社の社内システムとして、社員が購入申請や備品の利用を行います。一般向けの新規登録は設けません。

| 項目 | 前提 |
| --- | --- |
| 社員数 | 約100名 |
| 拠点 | 東京本社・大阪支社 |
| 東京本社の部署 | 営業部・開発部・管理部 |
| 大阪支社の部署 | 営業部・開発部 |
| 同名の部署 | 東京と大阪はそれぞれ上長がいる別々の部署 |
| 部署名 | 営業1部・営業2部、開発1部・開発2部のようには分けない |
| 各部署の役職 | 部長1名、課長2名、非管理職社員 |
| 課の構成 | 各部署に2つの課を置き、1名の課長が1つの課を担当する |
| 管理職 | 課長以上。承認者は管理職が担当する |
| 非管理職 | 一般社員・主任・係長などの細かな役職は、現時点では承認者として区別しない |

会話中の「大阪本社」「大阪支店」は、この文書では「大阪支社」に表記を統一します。全5部署で、上記設定から部長5名・課長10名となります。社員約100名・2拠点という設定は業務背景であり、登録人数・拠点数のシステム上限ではありません。

### 説明用の人物・組織例

以下の課名・人物名は説明用であり、正式なマスターデータや初期データではありません。

```text
東京本社 営業部：AAA部長
├─ 第1課：BBB課長 → DDDさんなどを担当
└─ 第2課：CCC課長 → EEEさんなどを担当

大阪支社 営業部：XXX部長
├─ 第1課：YYY課長
└─ 第2課：ZZZ課長
```

大阪の社員例はWWWさん・UUUさんですが、所属する課は未決定です。

## 業務の方向性（合意済み）

- 購入申請・承認・発注から、備品の貸出・返却・廃棄までを扱うアプリを題材にします。すべてを初期リリースに含めるとは決めていません。
- 部署の予算で購入し、部長が支出の妥当性を判断する責任を持ちます。
- 部長用の備品も社員が部署として申請します。申請者と備品の利用者は同一でなくてもよく、共用備品も対象です。
- 取引先の追加は購入申請とは別の機能として設ける方針です。登録権限や承認の要否は未決定です。
- 予算の確保・消化・残額管理は今後の機能候補とし、現在の認証・認可の要件定義では詳細化しません。

## 学習したい機能と未決定事項

認証・認可、ファイル出力、RDB、外部API、画像、非同期処理、メール、監査対応を、業務上の用途と結び付けて学びたいという希望があります。具体的な機能・導入順序・初期範囲は未決定です。

会社の業種・正式名称、課の正式名称、各課の人数、入社・異動・退職の運用、兼務の有無、管理部が両拠点を担当する範囲、備品管理担当者・アカウント管理担当者は未決定です。会社の業種をソフトウェア開発会社にする案や、管理部が発注・備品登録を担う案は、提案段階です。
